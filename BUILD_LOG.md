# Build Log

How this repo got from an empty folder to what's checked in today, exact
steps to rebuild it from scratch, and how the CI build channels work. If
you're onboarding onto this project or trying to reason about why a build
setting exists, start here before digging through `project.yml` comments
or old commit messages one at a time.

`XCODE_SETUP.md` still holds the day-to-day command reference (build, run,
test, open in Xcode). This doc is the history and the "why."

## Rebuild from scratch

What you'd actually type on a clean Mac to get from a fresh clone to a
running app:

```bash
# 1. Prerequisites: Xcode 15+ and xcodegen.
brew install xcodegen

# 2. Clone.
git clone <this repo> && cd landonkea-ytmusic-ios

# 3. Secrets. The app reads INNERTUBE_API_KEY from an xcconfig that's
#    gitignored on purpose (see Config/Secrets.example.xcconfig for why
#    it's still safe to bake a real value into CI: it's YouTube Music's
#    own public web client key, not a billed credential).
cp Config/Secrets.example.xcconfig Config/Secrets.xcconfig
# then edit Config/Secrets.xcconfig and replace YOUR_INNERTUBE_API_KEY_HERE
# with AIzaSyC9XL3ZjWddXya6X74dJoCTL-WEYFDNX30

# 4. Generate the Xcode project. It's gitignored, this step is required
#    after every fresh clone and after any project.yml change.
xcodegen generate

# 5. Build + run from the command line, or open in Xcode instead:
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
xcodebuild -project YTMusicApp.xcodeproj -scheme YTMusicApp \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -configuration Debug build
# or: open YTMusicApp.xcodeproj, then Cmd+R

# 6. Run the test suite (writes a summary to test-results/latest.md):
scripts/run_tests.sh
```

That's the whole path — no signing team, no Apple Developer account, and
no manual Xcode project surgery required. See `XCODE_SETUP.md` for the
simulator install/launch commands and the Mac Catalyst build flags.

## CI build channels

`project.yml` defines three build configs (`Debug`, `TestFlight`,
`Release`) and three matching schemes (`YTMusicApp-Dev`,
`YTMusicApp-TestFlight`, `YTMusicApp-Release`), each pinned to one config
so a scheme name alone tells you what you're building. Three GitHub
Actions workflows drive them:

| Workflow | Trigger | Scheme | What it produces |
|---|---|---|---|
| `.github/workflows/build-dev.yml` | push to `dev` | `YTMusicApp-Dev` | Debug-config simulator build, every push |
| `.github/workflows/build-testflight.yml` | tag matching `v*.*.*-*` (e.g. `v1.2.0-beta.1`) | `YTMusicApp-TestFlight` | Release-optimized simulator build |
| `.github/workflows/build-release.yml` | tag matching `v*.*.*` with no hyphen (e.g. `v1.2.0`) | `YTMusicApp-Release` | Release-optimized simulator build |

All three run `xcodebuild build` against an iOS Simulator destination,
the same unsigned local-build path `ci.yml` already uses, and upload the
resulting `.app` bundle as a workflow artifact. None of them archive,
sign, or upload anywhere — there's no Apple Developer account or signing
certificate wired into this repo's CI, so "TestFlight" here describes the
shape of the build (a Release config kept separate from stable, the way
a real TestFlight build would be), not an actual App Store Connect
upload. Turning one of these into a real signed archive later just means
adding a signing identity to CI and swapping `build` for `archive` on
that one workflow; the scheme and config split already does the rest.

The `TestFlight` config exists as its own thing rather than reusing
`Release` so it can diverge later, a beta feature flag, a different
bundle ID suffix, without touching what actually ships. Today both
configs inherit identical settings from Apple's `release` optimization
profile and point at the same `Config/Secrets.xcconfig`, so until that
divergence happens, the two builds are functionally the same binary
under different names.

## Notable decisions

**Single module instead of an `YTMusicAPI` framework.** The API layer's
types have no `public` access modifiers. Splitting it into its own module
would mean a large, mechanical, error-prone refactor for no behavior
change, so `project.yml` compiles `Sources/YTMusicAPI` straight into the
`YTMusicApp` target instead. `Package.swift` mirrors the same structure
so `swift build` type-checks correctly even though it can't produce a
runnable iOS binary.

**`.xcodeproj` is gitignored, `project.yml` is the source of truth.**
Xcode project files are enormous, diff-unfriendly, and prone to merge
conflicts when two branches touch build settings. `xcodegen generate`
regenerates the whole project deterministically from a ~280-line YAML
file, which is what actually gets reviewed in a diff.

**CloudKit instead of a custom sync backend.** Playlists and liked songs
sync through each user's own private iCloud database via raw
`CKRecord`/`CKDatabase` calls (not `NSPersistentCloudKitContainer` — see
`CloudKitSyncManager.swift` for why). No server to run, no accounts to
manage, and it's free at any scale a hobby project would hit. The
tradeoff: no deletion sync and no push-based `CKSubscription` yet, both
called out as known gaps in the README's CloudKit section.

**Entitlements files are committed, against the usual convention.** The
two `.entitlements` files are small, hand-authored, secret-free (just an
App Group ID). Leaving them gitignored, the default for Xcode-generated
files, would mean `CODE_SIGN_ENTITLEMENTS` points at a file that doesn't
exist on a fresh clone, and the build fails outright. `.gitignore`
explicitly un-ignores both.

**CI builds stay unsigned.** Every workflow in this repo, including the
new build channels, targets the iOS Simulator and skips code signing
entirely. There's no Apple Developer account attached to this project, so
CI can verify the app builds and its tests pass, but it can't produce
anything installable on a real device or uploadable to App Store Connect.
That's a deliberate boundary, not a gap to close casually — see the
"CI build channels" section above for what changes if that ever happens.
